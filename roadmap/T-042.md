## Goal

Re-enqueue demands left `pending` longer than `Extraction:StaleAfterMinutes`, at startup and every `Extraction:SweepIntervalMinutes`, so that no demand stays stuck after a restart, a full queue or a failed `fail` update (EXT-09).

## Context (read first)

- API spec EXT-09, EXT-01 (full queue), EXT-07 (last sentence), EXT-08, DEC-23, AT-46; architecture plan §11.3; [ARB-008](ARB-008.md).

## Scope

- **In:** `ExtractionSweepService` (Application: computes the threshold with an injected `TimeProvider`, lists stale ids in a bounded batch, enqueues them), `ExtractionSweepWorker` (Infrastructure `BackgroundService` with `PeriodicTimer`), registered in `AddExtractionProcessing()` (wired into `Program.cs` by T-043).
- **Out:** a message broker.

## Plan of actions

1. `ExtractionSweepService.SweepAsync(ct)`: `threshold = now(UTC) − StaleAfterMinutes`; `ListStalePendingAsync(threshold, batch)` (batch constant, e.g., 100 = `QueueCapacity`); `TryEnqueue` each; log count only.
2. Worker: run once at startup, then every `SweepIntervalMinutes`; exceptions logged and swallowed (next tick retries); stops on shutdown.
3. Duplicate hand-over across replicas is harmless (EXT-02/EXT-06) — no lock.
4. Tests: AT-46 — fresh `pending`, stale `pending`, stale `ok` → only the stale `pending` is enqueued and then processed (with fake extractor); `TimeProvider` fake to control time; failing repository does not stop the worker.

## Acceptance criteria

- [ ] AT-46 passes.
- [ ] Startup sweep + periodic sweep; bounded batch.
- [ ] No status change made by the sweep itself.
