## Goal

Provide the one shared `reloadDemands()` (architecture plan §6.2): never two list GETs in flight; a trigger during a GET schedules exactly one more; the displayed list is replaced only on success; the last good list is kept on error.

## Context (read first)

- Webapp spec DEM-04, DEM-05, DEM-06, RT-04, AC-06, AC-07, AC-22, AC-23, AC-24; architecture plan §6.2, §11.3.

## Scope

- **In:** composable exposing reactive `userName`, `demands`, `status` (`initialLoading | ready | error`), `hasError`, `isRetrying`, and `reloadDemands()`; tests.
- **Out:** triggers wiring (T-057), rendering (T-054).

## Plan of actions

1. State machine: `inFlight` promise + `pending` flag; `reloadDemands()` → if in flight, set `pending = true` and return the current promise; on completion, if `pending`, clear it and run exactly one more GET.
2. Success: replace `demands` and `userName`; clear error. Failure (any `ApiError`): keep previous list, set error (kind kept for messages: `forbidden` vs other).
3. No timers, no focus/visibility listeners, no polling (AC-23).
4. Tests: AC-22 (several triggers during a GET → max one in flight, exactly one follow-up), AC-07/AC-24 (error keeps previous list), AC-06 (one trigger → one GET), no GET without a trigger; fake timers show no scheduled calls.

## Acceptance criteria

- [ ] AC-22 and AC-23 pass; error preserves the list.
- [ ] Only this composable calls `listDemands`.
