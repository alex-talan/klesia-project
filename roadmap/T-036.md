## Goal

Implement operation `createDemand`: parse exactly two multipart parts (`gk_number`, `bae_file`), enforce the request limits so an oversized file yields `413` (not a transport error), call the use case and map its result to `201`/`400`/`413`/`415`/`422`/`503`.

## Context (read first)

- API spec §7.2 (parts, rules 1–10, status codes), DEC-10 (`201`, body = demand, **no `Location`**), DEC-20, §5.2, HOST-07; contract `createDemand`, `CreateDemandForm`; AT-23 to AT-30, AT-39, AT-48, AT-50, AT-56.

## Scope

- **In:** controller action, multipart reading, Kestrel/`FormOptions` limits aligned with `Upload:MaxPdfSizeMb` + overhead, integration tests.
- **Out:** IIS/App Service platform limits (T-083 documents them).

## Plan of actions

1. Action `[HttpPost("api/v1/demands")]`, `[Consumes("multipart/form-data")]` semantics: a non-multipart request → `415` problem (ensure the body is problem+json via T-015).
2. Read the multipart body with `MultipartReader` (streaming) or `Request.ReadFormAsync` with limits — choose the streaming approach to avoid buffering whole files when possible, but the PDF must be validated (magic bytes) before upload; document the choice.
3. Part rules → `400` problem: missing `gk_number` or `bae_file`; a part present twice; any unknown part (including `user_id`, AT-50); `errors` keyed by part name.
4. Limits: per-endpoint `RequestSizeLimit` and `FormOptions.MultipartBodyLengthLimit` = `MaxPdfSizeBytes` + a fixed multipart overhead (e.g., 64 KB, documented); exceeding → `413` problem (catch `BadHttpRequestException` with 413 / `InvalidDataException` from the form reader and convert).
5. Map use-case results: `Created` → `201` with `DemandResponse` (same record as list items: `demand_id`, `gk_number`, `bae_link` API path, `status: "pending"`), **no `Location` header**; `Invalid` → `400`; `TooLarge` → `413`; `Unprocessable` → `422`; `StorageUnavailable` → `503`.
6. Integration tests (fakes: repositories, store, notifier, queue, extractor double that blocks):
   AT-23 (201, body, next GET lists it first, `bae_link` path), AT-24, AT-25, AT-26, AT-27, AT-28, AT-29 (`401`/`403`, nothing stored), AT-30 (twice → two demands), AT-39 (201 returned without waiting for extraction; exactly one N-1 after commit), AT-48 (storage unavailable → `503`, nothing stored; insert failure → `500` and blob deletion attempted), AT-50 (`user_id` part → `400`), AT-56 (two blob names under the owner's `oid`); no `Location` header; logs contain no GK/file name/URL.
