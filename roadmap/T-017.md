## Goal

Behind the App Service front end, which terminates TLS, the API treats a forwarded HTTPS request as HTTPS and never loops on HTTPS redirection; forwarded headers are trusted only as the platform requires (HOST-02, AT-36).

## Context (read first)

- API spec HOST-02, AT-36, §5.2 last bullet; `klesia_api/CLAUDE.md` *Hosting* ("Do not add … forwarded-header workarounds … that belonged to the withdrawn Container Apps decision" — i.e., use the standard App Service mechanism, nothing custom).
- On App Service for Linux, the platform sets `ASPNETCORE_FORWARDEDHEADERS_ENABLED=true`, which makes ASP.NET Core process `X-Forwarded-For`/`X-Forwarded-Proto` (verify in current Microsoft documentation before relying on it; record the source).

## Scope

- **In:** decision and implementation of HTTPS handling, test AT-36.
- **Out:** platform settings (HTTPS Only, TLS 1.2 — T-083).

## Plan of actions

1. Check current Microsoft documentation for ASP.NET Core on App Service (Linux and Windows) regarding forwarded headers; record the link in the completion record.
2. Do **not** call `UseHttpsRedirection` in production (the platform's *HTTPS Only* redirects HTTP); if kept for local development, enable it only in Development.
3. If the platform variable is not guaranteed (Windows plan), configure `ForwardedHeadersOptions` with `XForwardedProto` (and `XForwardedFor`) **without** clearing `KnownNetworks/KnownProxies` globally unless the documentation for App Service requires it; justify the choice in a code comment of one line.
4. Integration test AT-36: request over HTTP to the test server with `X-Forwarded-Proto: https` → `Request.IsHttps` true (expose via a test-only endpoint in the test host, or assert no `307/308` redirect and absolute URLs built with `https`).
5. Test: no redirect loop (a request with `X-Forwarded-Proto: https` never receives a redirect).
