## Goal

Expose the anonymous liveness/readiness probe used by the App Service Health check: `200 {"status":"ok"}` when the process and SQL respond, `503 {"status":"unavailable"}` otherwise, with no dependency detail.

## Context (read first)

- API spec §5.3 (API-03), HOST-03, AT-22, AT-34; contract operation `getHealth` and schema `HealthResponse`; architecture plan §10.2.

## Scope

- **In:** health endpoint, a SQL health probe (Infrastructure, `SELECT 1` with a short timeout), tests.
- **Out:** checks of storage, SignalR or Document Intelligence (not specified).

## Plan of actions

1. Use ASP.NET Core health checks with one custom check `SqlHealthCheck` (Infrastructure) opening a connection and running `SELECT 1` with a short timeout (e.g., 5 s, constant or option-free — do not add a configuration key not in §6.1).
2. `app.MapHealthChecks("/health", new HealthCheckOptions { ResponseWriter = writes {"status":"ok"} or {"status":"unavailable"} with application/json; ResultStatusCodes Healthy→200, Degraded/Unhealthy→503 }).AllowAnonymous()`.
3. Exclude `/health` from the CORS requirement (not needed), keep `X-Correlation-Id`.
4. Never include exception messages, check names or durations in the body.
5. Tests: healthy fake check → `200` and exact body; failing check (fake throwing) → `503` and exact body; no token required; body validated against `HealthResponse` (manually now, by T-044 later).

## Acceptance criteria

- [ ] AT-22 and AT-34 pass (with a faked SQL probe).
- [ ] Anonymous, detail-free, exact bodies.
- [ ] No new configuration key.
