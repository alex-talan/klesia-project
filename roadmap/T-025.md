## Goal

Implement operation `listDemands`: the signed-in user's identity and all their demands, exactly in the contract shape, with `bae_link` = `/api/v1/demands/{demand_id}/bae`.

## Context (read first)

- API spec §5.1 (API-01, response schema and the 10 processing rules), DEC-09, DEC-21, DEC-24 (point 3), §4; contract `listDemands`, schemas `UserDemands`, `Demand`, `DemandStatus`; AT-01 to AT-12, AT-20, AT-21, AT-55.

## Scope

- **In:** `DemandService.ListAsync(Guid oid, ct)` (Application: allowlist → repository → result DTO), WebApi contract records (`UserDemandsResponse`, `DemandResponse` with explicit `[JsonPropertyName]` snake_case), `DemandsController` with `[HttpGet("api/v1/demands")]`, tests.
- **Out:** document route (T-028), creation (T-036).

## Plan of actions

1. Application `DemandService.ListAsync`: resolve user (T-021), call `ListByUserAsync(user.Id)`, return `UserDemandsResult(user.UserUniqueId, user.Name, demands)`.
2. WebApi records: `user_id` (string, GUID lower-case "D" format), `user_name`, `demands[]` with `demand_id` (int), `gk_number` (as stored), `bae_link` (built in one place, e.g., `BaeLink.For(demandId)` → `/api/v1/demands/{id}/bae`), `status` (code). No other property; no `null` fields.
3. Controller: no parameters; ignores any query/header `user_id` (AT-11); returns `200 application/json`.
4. Integration tests with in-memory `IUserRepository`/`IDemandRepository`:
   - AT-01, AT-02, AT-03, AT-05, AT-20 (`401`), AT-04, AT-06, AT-07 (`403`, identical bodies), AT-08 (empty list), AT-09 (several demands, exact JSON names and types), AT-10 (two users isolated), AT-11 (`?user_id=` and header ignored), AT-12 (repository throws → `500` sanitised), AT-21 (problem shape + `X-Correlation-Id`), AT-55 (every `bae_link` exactly the API path; no host/query; blob URL never present).
   - The body has exactly the contract properties (compare key sets).
5. Logs: no GK number, no `user_name`.

## Acceptance criteria

- [ ] Controller contains no business rule or SQL.
