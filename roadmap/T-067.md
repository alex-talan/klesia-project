## Goal

Independently review the complete backend against the security architecture (architecture plan §9) and API spec §6.2, and add automated tests proving that logs and error bodies never contain sensitive data.

## Context (read first)

- Architecture plan §3 (AP-03, AP-05, AP-06, AP-07, AP-10, AP-12, AP-14), §9, §11.1; API spec §4, §5.2, §6.2, EXT-10, NOT-04, DEC-24; `klesia_api/CLAUDE.md`; OWASP Top 10.

## Scope

- **In:** review report, log-redaction tests, secret scan, dependency audit, fixes of findings that do not change the contract (others → arbitrage proposal).
- **Out:** infrastructure security (T-079 to T-084).

## Plan of actions

1. Run the `security-audit` and `architecture-review` skills; check: layer references inward; no EF Core; no SQL built by concatenation (search for `$"` / `+` in SQL strings); identity only from token; fallback policy; identical `403`; no `AllowAnyOrigin`/credentials; no secret in tracked files; no blob URL/name, GK number, token, file name, e-mail or extracted value in logs, exceptions, problem bodies or SignalR messages.
2. Log-redaction tests with `TestLogSink`: run the main flows (list, document, create, negotiate, extraction success and failure) with recognisable sentinel values (a unique GK, a unique blob host, a unique token) and assert none appears in any captured log.
3. `dotnet list package --vulnerable --include-transitive`; record results; fix or justify.
4. Search the repository for keys/connection strings/SAS (`AccountKey=`, `SharedAccessSignature`, `sig=`, `Password=`).
5. Write the review report in the *Completion record* below (no new documentation file); create follow-up tasks for open findings.
