## Context

While starting T-043, the current frontend specification conflicts with the canonical contract and the implementation roadmap:

- Webapp specification §7.2 NEW-03 and §10 AC-10/AC-11 describe SIREN input, separator removal and nine-digit validation; AC-14 and NEW-06 also retain SIREN wording.
- `contracts/openapi.yaml` defines `gk_number` as `^GK[0-9]{6}-[0-9]{9}$`, and its POST form schema uses `gk_number`.
- Root and webapp `CLAUDE.md`, plus T-042, T-043, T-049, T-054 and T-056, describe GK-number behavior.

T-043 cannot implement the stated examples and acceptance criteria consistently until the owning frontend specification is reconciled with the canonical contract. Related parsing, POST, list-rendering and modal work must not independently choose one convention. T-042 is already complete against the current contract; if the decision reverses the contract, a follow-up change will be needed for that completed model and any affected backend implementation.

## Questions

1. Should the frontend specification be corrected to use GK numbers and `gk_number`, matching the current OpenAPI contract and roadmap tasks, or should the contract and implementation plan be revised to restore SIREN behavior?
2. Which owner approves the corresponding specification/contract synchronization and any follow-up task list?

## Options

| Option | Consequence |
|---|---|
| A. Align the webapp specification with the current GK contract (recommended) | Update NEW-03, AC-10/AC-11, and remaining SIREN wording to GK behavior; keep the existing OpenAPI schema and roadmap implementation direction. |
| B. Restore SIREN behavior | Requires an approved contract change, API/backend changes, and follow-up work for the already completed frontend model and dependent tasks; potentially breaking to existing API consumers. |

## Recommendation / provisional default

Recommend option A because the canonical OpenAPI contract, root/app instructions and current task plan consistently use GK numbers. This arbitrage remains blocking until the project owner confirms the direction and the owning documents are synchronized.

## Decision

| Field | Value |
|---|---|
| Decision | Keep GK numbers and `gk_number` as canonical. The current frontend specification aligns with the OpenAPI contract; no contract change is required. |

### Answers

1. Should the frontend specification be corrected to GK or should the contract return to SIREN? — Option A: keep GK and `gk_number`. The current frontend specification has already been updated to match.
2. Which owner approves the synchronization and follow-up tasks? — Project owner + tech lead.

### Rationale and consequences

The current webapp specification now defines GK input, GK normalization and the `gk_number` POST part; OpenAPI and the API creation contract use the same format. Remaining SIREN references in the API specification concern extracted company data, not demand identifiers. The completed T-042 model remains valid. No contract change or additional synchronization task is needed. T-043, T-048, T-049, T-054 and T-056 may proceed when their other task dependencies permit.
