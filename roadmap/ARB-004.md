# ARB-004 — Server-side Azure SignalR integration

| Field | Value |
|---|---|
| Number | ARB-004 |
| Subject | Server-side Azure SignalR integration |
| Description | Management SDK or raw REST, Azure role of the identity, access keys in dev or managed identity only |
| Blocking | YES |
| Concerning tasks | `T-030`, `T-031`, `T-078`, `T-079` |
| Status | OPEN |

## Context

- API spec §8.1 / NOT-01: Azure SignalR Service in **Serverless** mode, hub `demands`; negotiate returns `{url, accessToken}` with `userId` = `oid`; the notifier sends a user-targeted `demandUpdated` with no arguments through the REST API, **with the managed identity and no access key**.
- §8.1 states the infrastructure contract assigns **SignalR Service Owner** and asks to "verify that resource mode and role assignments are consistent at implementation time".
- `klesia_webapp/infra/azure-signalr/README.md` keeps **access keys enabled in dev** "for local development convenience", which contradicts "no access key" for the API.
- Generating a client access token with Microsoft Entra authentication requires a role that allows the `auth/accessKey` / client-token action; publishing requires a REST role. The exact built-in roles must be checked against current Azure documentation.

## Questions

1. Server library: `Microsoft.Azure.SignalR.Management` (`ServiceManager`, `ServiceHubContext`, `NegotiateAsync`, `Clients.User(oid)`) or hand-written REST calls with an Entra token from `Azure.Identity`?
2. Which built-in role does the user-assigned identity receive (*SignalR Service Owner*, *SignalR REST API Owner*, *SignalR App Server*, …)?
3. In dev, are access keys allowed for local runs, or must developers use their own Entra identity with a role on the dev resource?

## Options

| Option | Notes |
|---|---|
| A. Management SDK + `DefaultAzureCredential` + one role covering negotiate and publish (recommended) | Least custom code; SDK handles token generation and REST calls; verify the role on a dev resource. |
| B. Raw REST + hand-written client-token generation | No extra package but security-sensitive custom code (token signing); not recommended. |

Dev keys: recommended **managed identity / developer identity only**, `disableLocalAuth: true` in every environment, consistent with HOST-04 and BE-05.

## Recommendation

Option A, Entra authentication everywhere, role verified on the dev resource before T-078/T-079.
