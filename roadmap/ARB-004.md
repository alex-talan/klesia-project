## Context

- API spec §8.1 / NOT-01: Azure SignalR Service in **Serverless** mode, hub `demands`; negotiate returns `{url, accessToken}` with `userId` = `oid`; the notifier sends a user-targeted `demandUpdated` with no arguments through the REST API, **with the managed identity and no access key**.
- §8.1 states the infrastructure contract assigns **SignalR Service Owner** and asks to "verify that resource mode and role assignments are consistent at implementation time".
- `klesia_webapp/infra/azure-signalr/README.md` keeps **access keys enabled in dev** "for local development convenience", which contradicts "no access key" for the API.
- Microsoft documents **SignalR Service Owner** as granting all data-plane APIs, including REST and authentication/token APIs, and recommends it for Serverless negotiation. **SignalR REST API Owner** is REST-focused and does not handle negotiation.

## Questions

1. Server library: `Microsoft.Azure.SignalR.Management` (`ServiceManager`, `ServiceHubContext`, `NegotiateAsync`, `Clients.User(oid)`) or hand-written REST calls with an Entra token from `Azure.Identity`?
2. Which built-in role does the user-assigned identity receive (*SignalR Service Owner*, *SignalR REST API Owner*, *SignalR App Server*, …)?
3. In dev, are access keys allowed for local runs, or must developers use their own Entra identity with a role on the dev resource?

## Options

| Option | Notes |
|---|---|
| A. Management SDK + `DefaultAzureCredential` + one role covering negotiate and publish (recommended) | Least custom code; SDK handles token generation and REST calls; verify the role on a dev resource. |
| B. Raw REST + Azure.Identity | Entra-authenticated REST can call the `generateToken` endpoint; it avoids hand-signing a JWT but requires custom HTTP, token-response and error handling. |

Dev keys: recommended **managed identity / developer identity only**, `disableLocalAuth: true` in every environment, consistent with HOST-04 and BE-05.

## Recommendation

Option A, Entra authentication everywhere, role verified on the dev resource before T-079/T-080.

## Decision

| Field | Value |
|---|---|
| Decision | Use the Azure SignalR Management SDK with `DefaultAzureCredential` for negotiation and targeted publishing; assign SignalR Service Owner to the API identity at the SignalR resource; use each developer's Entra identity for local runs and disable local authentication. |

### Answers

1. Server library — `Microsoft.Azure.SignalR.Management` (`ServiceManager` / `ServiceHubContext`) with `DefaultAzureCredential`, shared for negotiation and publishing.
2. Built-in role — SignalR Service Owner, scoped to the individual SignalR resource.
3. Local development — developer Entra identity via `DefaultAzureCredential`; no access keys, with local authentication disabled.

### Rationale and consequences

The Management SDK covers the shared Serverless negotiation and user-targeted publish path without custom REST handling. SignalR Service Owner covers both token/negotiation and REST operations. This is consistent with the API specification's managed-identity/no-access-key requirement; the API contract also states that the Azure access key is never returned and the backend reaches SignalR with managed identity. The raw-REST option was corrected above: Entra-authenticated `generateToken` does not require hand-signing a JWT, but would add custom request and error handling.

T-030 is unblocked. T-031 remains blocked until T-030 is complete. T-058 remains blocked by T-031, its other unfinished task dependencies, and pending external dependencies. T-079 and T-080 remain blocked by ARB-009 and ARB-010. No new follow-up task is needed: T-079 already covers `disableLocalAuth: true` and the operator README update; it will apply this decision when its other gates are settled.
