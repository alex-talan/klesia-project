## Goal

Prove, with a reproducible demo, the first demonstrable stage of KLESIA (milestone M1, [roadmap.md](roadmap.md) §8), running **locally** against **real** Entra ID and the **dev** Azure SQL, Blob Storage and SignalR resources:

1. the signed-in user sees the list of their demands and can open a demand's BAE PDF;
2. the user creates a demand: the PDF is copied to the private Blob container, the row is inserted with status `pending`, the backend sends **N-1** and the frontend reloads the list through SignalR — **no extraction, no Document Intelligence call**: the new demand stays "En cours".

## Plan of actions

1. **Prerequisites (from the EXT items).** Record *where* each value is (never the values themselves if sensitive):
   - EXT-001: tenant id, API app id (v2 access tokens, scope `access_as_user`), SPA app id with the redirect URI `http://localhost:5173/redirect.html`;
   - EXT-003: dev Azure SQL server/database; your Entra account is a database user with the grants of `local-development.md` §2; your IP allowed;
   - EXT-005: dev storage account + private container; your account has *Storage Blob Data Contributor* on it;
   - EXT-006: dev Azure SignalR Service in Serverless mode, CORS `http://localhost:5173`, your account has the role decided in ARB-004.
2. **Database.** Build and publish the DACPAC to the dev database (`local-development.md` §5), after reviewing the generated script (`/Action:Script`). Make sure the demo user's Entra `oid` is in `sec.User` and active (seed `02_User.sql` or an operator insert — never committed with a real third-party identity unless ARB-019 allows it).
3. **API configuration** in `klesia_api/src/WebApi/appsettings.Local.json` (git-ignored; verify with `git check-ignore`): `ConnectionStrings:KlesiaDb` (passwordless), `AzureAd:*`, `Cors:AllowedOrigins = ["http://localhost:5173"]`, `Storage:BlobServiceUri`, `Storage:ContainerName`, `AzureSignalR:Endpoint`, `Upload:MaxPdfSizeMb` (= the webapp value, ARB-002). No `DocumentIntelligence` value is needed. `az login` with the account holding the roles.
4. **Webapp configuration** in `klesia_webapp/.env.local` (git-ignored): `VITE_API_BASE_URL=http://localhost:5180`, `VITE_SIGNALR_HUB_URL=http://localhost:5180/api/v1/notifications`, `VITE_ENTRA_*`, `VITE_API_SCOPE`, `VITE_ENTRA_REDIRECT_URI=http://localhost:5173/redirect.html`; `public/config/app-config.json` `maxPdfSizeMb` equal to the API value.
5. **Run.** `dotnet run --project src/WebApi --launch-profile http` (in `klesia_api`) and `npm.cmd run dev` (in `klesia_webapp`). Check `GET http://localhost:5180/health` → `200 {"status":"ok"}`.
6. **Demo script** (two browser windows side by side, the second one signed in as the same user to show the targeted notification; developer tools open on the network tab):
   1. Sign in → the header shows the user's name; the list loads (empty state "Aucune demande d'adhésion." or existing demands); the connection status line is absent (hub connected).
   2. Click "Nouvelle demande" → enter a GK number such as `gk260902-144743112 ` → select a PDF → OK.
   3. The modal closes; **no** list `GET` is sent by the `POST` success; then `demandUpdated` arrives (N-1) and exactly one list `GET` runs; the new demand appears first as "En cours" in **both** windows.
   4. Click the GK number of the new demand → a new tab shows the PDF (object URL); the request carries the Bearer token to the API origin only.
   5. Submit the same GK number again → a second, distinct demand appears (duplicates allowed, INT-09).
   6. Optional negative checks: an invalid GK number shows the inline French error and sends nothing; a non-PDF file is refused client-side.
7. **Evidence.** In the Azure portal (or `az storage blob list --auth-mode login`): the blob exists under `{oid}/{guid}.pdf`; in the database: the row has status `pending` and a `CreatedAt`; the API log shows the N-1 publish and no extraction activity; no token, GK number or blob URL appears in the API or browser console logs.
8. Write `roadmap/reports/T-058-demo-m1.md`: prerequisites (where, not values), commands, the checklist with pass/fail per step, observations, known limits (no extraction; demands stay `pending`; the recovery sweep enabled by T-065 will later process these `pending` demo demands unless the dev data is cleaned).
