## Goal

Provide the passwordless SQL connection factory and the `IUserRepository` port with its Dapper implementation that reads an allowlist entry by Entra `oid`.

## Context (read first)

- API spec DEC-02, DEC-06, DEC-12 (aliases), DB-12, §4.2 (lookup), §6.2 (parameterised SQL, never concatenate), `klesia_api/CLAUDE.md` §4.
- Architecture plan §8.2 (identity distinction).

## Scope

- **In:** `ISqlConnectionFactory` (Infrastructure-internal), `IUserRepository` (Application), `UserRepository` (Infrastructure), DI registration, unit tests where meaningful.
- **Out:** the allowlist decision logic (T-021), constraint tests (T-013).

## Plan of actions

1. `SqlConnectionFactory`: creates `SqlConnection` from `ConnectionStrings:KlesiaDb` (Microsoft.Data.SqlClient handles `Authentication=Active Directory Default` and `AZURE_CLIENT_ID`); returns closed connections; opened by callers with the cancellation token.
2. `IUserRepository.GetByUniqueIdAsync(Guid oid, CancellationToken)` → `ApplicationUser?` (with `IsActive`; the active check is done by T-021, so the repository returns inactive users too).
3. SQL: `SELECT u.Id AS Id, u.UserUniqueId, u.Name, u.IsActive FROM sec.[User] AS u WHERE u.UserUniqueId = @Oid;` with a `DbType.Guid` parameter; `CommandDefinition` with the token.
4. Register `ISqlConnectionFactory` (singleton) and `IUserRepository` (scoped) in `AddInfrastructure`; add the `Dapper` and `Microsoft.Data.SqlClient` references (already present in `Infrastructure.csproj`).
5. No logging of the `oid` together with other user data; dependency failures propagate as exceptions (mapped to `5xx`, never `403`).
6. A database-backed test of the query belongs to T-013-style opt-in tests (add one case: lookup of an existing and a missing `oid`, skipped without the variable).

- [x] Parameterised SQL only; no string interpolation.
