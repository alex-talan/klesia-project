## Goal

Implement step 1 of the workflow (§7.2) in `DemandService.CreateAsync`: allowlist → validate → upload the PDF → insert the `pending` demand → **after the commit** publish N-1 (best effort) → enqueue the id (never failing) → return the created demand.

## Context (read first)

- API spec §7 table, §7.2 rules 1–9, DEC-13, DEC-17, DEC-20, NOT-02, NOT-03, NOT-05, EXT-01, INT-09; architecture plan §7.4 (read-after-write), §8.4 (*Write* flow).
- Why T-030 is a dependency: the composition root must register a real `INotifier` once `DemandService` depends on it (startup validation of the DI graph in Development).

## Scope

- **In:** use-case method, result type, unit tests with fakes.
- **Out:** HTTP/multipart (T-036).

## Plan of actions

1. Signature: `CreateAsync(Guid oid, CreateDemandInput input, CancellationToken ct)` → `CreateDemandResult` (`Created(Demand)`, `Invalid(errors)`, `TooLarge`, `Unprocessable(errors)`, `StorageUnavailable`).
2. Order (rule 1 first): resolve user (`403` path) **before** validating or touching storage; then validate (T-032); nothing stored on failure.
3. Upload via `IBaeDocumentStore.UploadAsync(user.UserUniqueId, stream)`; `DocumentStoreUnavailableException` → `StorageUnavailable` (`503`), nothing stored.
4. `CreatePendingAsync(user.Id, gk, blobUrl)`; on exception → best-effort `DeleteAsync(blobUrl)` (catch and log its failure without URL) → rethrow (→ `500`).
5. After the insert committed: `await notifier.NotifyDemandsChangedAsync(user.UserUniqueId)` inside a try/catch (never alters the result); then `queue.TryEnqueue(id)` (ignore `false`, already logged).
6. Return `Created(new Demand(id, user.Id, gk, Pending))`.
7. Never log GK, file content or URL.
8. Unit tests: happy path call order (upload → insert → notify → enqueue) and arguments (`oid` from the resolved user, not input); inactive user → nothing called; invalid GK → nothing called; storage unavailable → no insert, no notify; insert fails → delete attempted, no notify, no enqueue; notifier throws → still `Created`, enqueue still done; queue full → still `Created`; same GK twice → two inserts with different blob names (AT-30, AT-56 at unit level).

## Acceptance criteria

- [ ] Order and guarantees of §7.2 enforced and unit-tested.
- [ ] N-1 strictly after the commit, best effort; enqueue never fails the request.
- [ ] No user id read from input (DEC-20).
