# ARB-019 — Allowlist population per environment

| Field | Value |
|---|---|
| Number | ARB-019 |
| Subject | Allowlist population per environment |
| Description | Which users are seeded in each environment and how `02_User.sql` varies by environment |
| Blocking | YES |
| Concerning tasks | `T-084`, `T-089` |
| Status | OPEN |

## Context

- DEC-05: `Scripts/02_User.sql` is insert-only, matched on the Entra `oid`, and seeds the project owner as an active `admin`. Further identities are added by editing the script. There is no user-management API (§1.2).
- The same DACPAC is published to every environment, so today every environment receives the same users.
- Roles grant nothing (OPEN-04).
- The `sec.User` defaults are not fail-closed (`IsActive` = 1, `RoleId` = 1) — harmless while users are only seeded explicitly (§3.3 defaults note).

## Questions

1. Which users must be allowlisted in dev, staging and production?
2. Should the developer/test accounts be excluded from production?
3. Mechanism: SQLCMD variable (e.g., `$(Environment)`) selecting a block in `02_User.sql`, separate per-environment scripts, or seeding production users through an operator procedure outside the DACPAC?
4. Who maintains the production allowlist and how is a user deactivated (operator `UPDATE IsActive = 0`)?

## Recommendation

A SQLCMD variable `Environment` passed by the pipeline; `02_User.sql` keeps a common block (none) and per-environment blocks; production users provided by the client; deactivation by an operator procedure documented in the deployment guide.
